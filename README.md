# The Becoming Conference — frontend

Independent **TypeScript** frontend with responsive HTML/CSS. Browser source lives in `src/`; `server/server.ts` is the small frontend web server/API proxy. This service has no MongoDB driver, database credentials, or backend source dependency.

## Start locally

Use Node.js 22.13 or newer. From this directory:

```powershell
npm install
# Only if .env does not already exist:
Copy-Item .env.example .env
npm run build
npm start
```

Open **http://localhost:3000**. Start the separate backend from `../backend` on port 4000. For subsequent edits, run `npm run build` again. `npm run dev` builds and starts the frontend. No root-level install or shared node_modules is required.

| Variable | Purpose |
| --- | --- |
| `PORT` | Frontend port, defaults to 3000 |
| `BACKEND_URL` | Backend origin, defaults to `http://localhost:4000`; server-only, HTTPS required in production |
| `NODE_ENV` | Set `production` for HTTPS security headers |
| `API_PROXY_SECRET` | Same server-only random value as backend, at least 32 characters; required in production; matching local values are already generated |
| `TRUST_PROXY` | 1 only behind exactly one trusted hosting edge that overwrites forwarded headers; otherwise 0 |

The frontend proxies `/api/*` to `BACKEND_URL`, preserving request Origin and the authenticated session cookie. This lets the services be hosted separately while the browser keeps its HttpOnly cookie on the frontend domain. Configure backend `APP_ORIGIN` to the exact frontend origin and use the same `API_PROXY_SECRET` in both server environments. The proxy authenticates itself and forwards the client IP for per-attendee rate limits; it replaces visitor-supplied proxy credential/IP headers. When `TRUST_PROXY=1`, the frontend uses the last IP supplied by its trusted edge; ensure visitors cannot bypass that edge or supply unverified forwarded headers. No hardcoded production domain or browser-exposed secret is used. The web server checks the backend session before serving `/admin` or `/admin.html`; API authorization is independently enforced by the backend.

## Try registration and export

1. Open `/`, enter all required attendee and guardian fields, and use international phone numbers beginning with `+`, e.g. `+2348031234567`.
2. Enter age as a whole number from 0 to 120. For someone under 18, their parent/legal guardian must complete the form and provide consent.
3. Complete registration. The success screen displays the conference date and registration ID. Invalid inputs produce field-specific errors; failures preserve the entered values.
4. Create an admin using the backend’s `npm run admin:create`, then open `/admin/login` on the frontend and sign in. The frontend must be deployed as a Node web service, not a static site, because its server protects `/admin` and proxies `/api/*`.
5. Search by name/email/school, filter by UTC registration date, and navigate pages. Open Details only when guardian contacts or age are needed.
6. Click **Download All Registrations (CSV)**. It downloads every current record regardless of the table’s filters or current page. Open the file in Excel or Google Sheets. Retry the same button after an error.

## Verification

```powershell
npm run typecheck
npm run build
npm test
```

Strict TypeScript checks both browser and frontend-server source. Tests cover form success/failure, retained values, duplicate-submit protection, admin HTML authentication, static asset security and proxy behavior. They use DOM test doubles and HTTP integration tests; they do not constitute visual/browser accessibility verification. See backend `docs/IMPLEMENTATION.md` for actual results.

## Separate deployment

Deploy **this directory** to a Node hosting service, with build command `npm install && npm run build` and start command `npm start`. Set production `BACKEND_URL` to the separately deployed backend’s HTTPS origin. Set `NODE_ENV=production`, configure HTTPS at the hosting edge, and use the frontend URL as the public registration link. Install development dependencies during the build because they contain TypeScript; runtime needs only Node and the generated assets/server.

For Vercel, deploy this directory as the project root and keep the default build command (`npm run build`). Set `BACKEND_URL` to the backend HTTPS origin and configure the same `API_PROXY_SECRET` as the backend. Explicit rewrites send `/api/*` to `api/gateway.ts`, `/admin` to `api/admin.ts`, and `/admin/login` to `api/admin-login.ts`; do not deploy Vercel as a static-only export.

`public/*.js` and `dist/` are generated by the build. Do not edit them directly or commit `.env`. Keep the `public/` directory in the runtime deployment. The default frontend needs a Node runtime: deploying only static files would bypass the authenticated HTML gate and remove the API proxy. A static hosting provider can instead supply equivalent protected routes and a same-origin reverse proxy, but that configuration is not included here.

Responsive layouts, labeled inputs, keyboard focus, error associations, status/alert regions, and a native accessible details dialog are implemented. No venue, fee, speaker list, payment, email confirmation or ticket issuance is invented. The privacy page identifies organizer-owned details that must be finalized before launch.

Existing DOB records are preserved, with age at registration derived for details/export. Existing application DOB collection validators are upgraded compatibly at startup.

Current form update: gender, numeric age, and date of birth are required. Gender options are Female, Male, Non-binary, and Prefer not to say. DOB is validated as a real, non-future calendar date and age must match DOB. Gender and both age fields are saved, shown in the protected admin view, and exported. Existing age-only records retain a blank DOB and older records without gender remain readable; no value is invented.
